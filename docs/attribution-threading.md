# Attribution on the verdict thread

A decision note, not a description of the code. It exists because
"attribution off the queue thread" has been an open item long enough to be
assumed correct, and it is not: the two obvious versions of it hand an
unprivileged local process the ability to choose the verdict for every
connection on the host. What the code actually needs is smaller than a
threading change and can be done without one.

Read `docs/ARCHITECTURE.md` first, in particular "The life of one packet"
step 4 and "Threads and tasks". This note assumes both.

## What a miss costs today

`decide` calls `AttributionChain::connection` as the first thing it does
(`nfqueue.rs:161`), on the one thread that must never block. Behind the cache
there are two sources, tried in order, first hit wins (`mod.rs:86`).

The eBPF source is O(1): one map lookup (`ebpf.rs:171`), then a
`/proc/<pid>/stat` read and, on a cold pid, a handful of bounded per-process
reads. It is already primary when the feature is built and the programs load.

The procfs source is the expensive one, and it is two separable halves:

- **address to (inode, uid)** (`procfs.rs:124-131`). Its comment says "stream
  both tables lazily", and that is only true of the parsing: the
  `read_to_string` inside the `.collect()` on line 127 reads
  `/proc/net/tcp` **and** `/proc/net/tcp6` in full, unconditionally, before a
  single line is parsed. On a host with tens of thousands of sockets that is
  megabytes regenerated by seq_file per miss, taking the kernel's hash-bucket
  locks on the way. Whoever reads that comment will believe this half is
  already cheap. It is the more expensive half.
- **inode to pid** (`procfs.rs:150-172`), a readdir of `/proc` plus a readdir
  and a readlink of every `/proc/<pid>/fd/*` until the inode is found, and
  then `verified_proc_details` (`procfs.rs:179-191`) runs `pid_holds_inode`
  a second time on the winner. Neither the number of pids scanned nor the
  number of fds scanned per pid is bounded.

The cache does not blunt any of this on the path that matters. Its key is the
whole `FlowTuple` (`cache.rs:47`), so a fresh ephemeral port is a miss by
construction, and `ct state new` is the only thing judged: essentially every
connection that reaches the rule engine is a cache miss by design.

So the cost of one connection is O(all sockets on the host) + O(all pids x
their open fds), synchronous, with no deadline, on the thread that decides
every other connection. One unprivileged process with a large fd table
inflates the second term for **everyone**, not only for itself.

## The three options, and why each is refused as posed

### A. Attribution on a worker with a hard per-packet deadline

The mechanics work: the held-packet map, the sequence numbers and the verdict
channel that the prompt path already uses would carry it, and a deadline
sweep on the queue loop needs no timer task. That is not the problem.

The problem is what happens when the deadline fires. Seven rule operands
depend on attribution: `exe`, `exe_glob`, `exe_sha256`, `hashes_file`, `user`,
`cmdline_contains`, `parent_exe`. With the fields unset, every one of them
fails to match (`model.rs:220-303`). So the fallback verdict is not "the same
decision with less information", it is a different policy:

- fall through to lower-priority rules, and a high-priority
  `deny exe=/path/to/malware` is deleted by being slow;
- fall back to allow, and every identity-scoped rule on the host stops
  applying for as long as the load lasts;
- fall back to deny, and every new connection on the host fails, which is a
  network outage an unprivileged local account can trigger at will.

The slow resource is global, so the attacker sets the expiry rate for the
whole host and picks whichever of those they want. Today the same primitive
only stalls the verdict thread. Option A as posed upgrades a stall into a
policy decision the attacker makes, which is strictly worse.

Two further costs that are easy to miss. `nfq::Message` pins the receive
buffer, so holding becomes the rule rather than the exception and the loop's
allocation-free receive path is defeated on every packet. And the kernel
queue is 1024 entries deep (nothing calls `set_queue_max_len`); a held packet
occupies a slot for the whole deadline window, so at ordinary connection rates
the queue fills, and an overflowed queue is resolved by the `bypass` flag
alone, with no event and no counter.

### B. An incrementally maintained inode to pid index

It addresses the cheaper half. The `/proc/net` read has to stay regardless,
because `uid` is taken from that row (`procfs.rs:141`) and `user` is a rule
operand, so the complexity class of a miss does not change.

There is also no feed for it on the hosts that need it. procfs generates no
inotify events; the netlink proc connector carries fork/exec/exit and no fd or
socket event at all; fanotify does not see sockets; and the "eBPF sock
tracepoints we already have" do not exist, `inode`, `i_ino` and `sk_socket`
appear nowhere in the eBPF crate. Where eBPF does load, the existing
`SOCK_MAP` already answers tuple to pid in one lookup and procfs is never
consulted, so an index there is a worse copy of a map that exists. Where eBPF
does not load, which is exactly the population that pays for the walk, the
only available feed is the walk itself, and a walk-fed index is cold for
precisely the entries it will be asked about: every `ct state new` TCP
connection uses a socket created after the previous walk.

It would also change which pid is returned when several hold a socket (fork,
SCM_RIGHTS): today `/proc` readdir order makes it deterministically the lowest
holder, and an index makes it whichever was seen last. That is a silent change
to `exe` matching that no test would catch.

### C. Require the eBPF attributor, procfs best-effort

The premise is already true: eBPF is first in the chain and procfs is only
consulted on a miss. So this option is not "make eBPF primary", it is "delete
the fallback", and the fallback is what makes eBPF's blind spots survivable.
The code says so itself, at `ebpf.rs:188-189`: a wrong offset default "only
costs eBPF lookup misses, which the procfs attributor absorbs".

The miss set is attacker-selectable: an unconnected UDP `sendto` stores a
wildcard source address in the key and never matches the packet's tuple; there
is no probe on `raw_sendmsg`; and `SOCK_MAP` holds 8192 entries with LRU
eviction, which a burst of connects flushes. Delete the absorber and each of
those becomes "no attribution", which means exe-keyed and user-keyed **deny**
rules stop firing. That is a fail-open evasion primitive.

It is worse on a kernel with no BTF and a non-x86_64 `sock_common` layout,
where the offsets fall back to compiled-in defaults: every lookup misses while
the journal says "eBPF attribution active" and nothing in `hallpass-cli
status` disagrees.

And the distribution cost is disqualifying on its own. The default build is
procfs-only stable Rust by design (`CONTRIBUTING.md`), and `install.sh`
silently degrades to it when the eBPF build fails. Under a strict version of
this option that configuration is a firewall with no process identity at all,
which is to say nftables with DNS names bolted on.

## Recommendation

Bound the unbounded work where it is, rather than moving it or deleting it.
Everything below is smaller than any of the three options, and none of it
changes which thread anything runs on. Items 1, 2 and 4 have landed; item 3
is the one still open, and it needs a dependency decision before any code:
the daemon denies `unsafe_code`, so a raw netlink socket means taking on a
netlink crate and defending it at `cargo deny`, or finding another way to
ask.

**1. Cap the executable hash** (`hash.rs:87-98`). **Done.** `std::io::copy` into the
hasher has no size cap and no regular-file check, and it runs inline on the
verdict thread. The gate in front of it is not the mitigation it looks like:
an unscoped `hashes_file` blocklist rule, which is the canonical way to write
one, has no other criteria and so matches every new connection, and the daemon
then hashes whatever binary the process just exec'd. The `FileId` key is taken
by fstat on the already-open fd, so the cache cannot be poisoned by a path
swap, but a fresh file is a fresh key, so the cost is repeatable at will.
Refuse anything that is not a regular file, skip over a size cap, count the
skip. The failure direction is already documented for `exe_sha256`: a rule
that cannot verify a binary does not match it.

**2. Bound the fd scan per pid, not per attribution** (`procfs.rs:164-172`).
**Done**, with one addition: a per-process cap alone does not bound the walk,
because the walk visits every process, so there is a total cap as well. The
two together mean no single process can take more than a quarter of the
budget, which is the property a shared budget alone would not have had.
This distinction is the whole point. A budget spent across the whole walk lets
one process with a million fds exhaust it and cost every *other* process its
attribution, which is option A's failure with extra steps. A budget per pid
costs only the process that is over it: the scan of that pid gives up, the
walk continues, and every legitimate attribution still succeeds. Set it high
enough that no ordinary process reaches it, count and log the ones that do.
A process that hides from attribution this way gains nothing it did not
already have (see the exec-after-connect limitation in the README).

**3. Ask the kernel for one socket instead of dumping them all.** A
`NETLINK_SOCK_DIAG` `inet_diag_req_v2` carrying the 4-tuple is a hash lookup
in the kernel that returns the inode and the uid, in place of an O(all
sockets) seq_file dump of two tables. Same information, same semantics, and it
removes the larger half of a miss outright. Keep the file read as the fallback
for a kernel without the diag module, which is also what keeps the existing
tests meaningful.

**4. Fix the comment at `procfs.rs:122-123`**, which describes a laziness the
`.collect()` on the next line removes. **Done.**

Only if those are done and measured and still not enough: a deadline whose
granularity is **per source, not per packet**. Run the bounded sources inline,
run procfs on a worker under a deadline, and on expiry use whatever the
bounded sources returned rather than inventing a fallback verdict. That
degrades to "eBPF's answer" under the feature and to "no answer" without it,
which is honest, and it never converts latency into a verdict.

## The finding that outranked all of this (fixed)

Left here because the reasoning is why the fix looks the way it does.

`cached_still_valid` asked two questions: does `/proc/<pid>` exist, and does
its `exe` symlink still read the same. Neither establishes that the recorded
process still owns *this flow*.

The cache is keyed on the 5-tuple with a 60 second positive TTL
(`cache.rs:14-16`). A process reads a victim's live tuple from world-readable
`/proc/net`, waits for that socket to close, and binds the same source port to
the same destination inside the window. The victim is still running its
original binary, so the check passes and the flow is judged as the victim:
its uid, exe, cmdline and parent exe. `exe_sha256` matches too, because the
hash is taken from the live victim binary. On a default-deny host that is a
bypass of every identity-scoped allow rule for that destination, and the
event stream records the victim's name for the connection.

`uid`, `cmdline` and `parent_exe` were not checked at all, and each is a rule
operand.

The fix does not re-resolve the tuple, which would cost the whole of half 1
on every cache hit. A source port only becomes free to reuse once the socket
behind it is closed, and the kernel hands out a fresh inode per socket, so
"does the recorded process still hold the recorded socket inode" answers
exactly the right question for the price of one `/proc/<pid>/fd` readdir.
`ProcInfo` carries the inode and the start time to make that possible; the
start time was already the primitive the eBPF detail cache used for pid
recycling, and had simply not been applied here. Entries with no inode, which
is what the eBPF source produces, are never served: that map is keyed by the
same tuple and the connect that reused the port has already overwritten it,
so asking it again is cheaper than the check and more current than the cache.

The positive TTL is deliberately left at 60s. With the ownership check in
front of it the TTL is no longer what bounds staleness, and shortening it
would only cost hit rate.

## Re-checked audit leads

The leads listed in the handoff were reported by a review that never verified
them. Checked against the code:

| Lead | Verdict |
| --- | --- |
| `hash.rs:94` unbounded synchronous hashing on the packet path | Confirmed. Recommendation 1. |
| `attribution/mod.rs:82` cached positive-hit revalidation scope | Confirmed, larger than reported, and fixed. See above. |
| `attribution/ebpf.rs:149` exec snapshot keyed on (pid, starttime) | Confirmed, with a caveat. starttime survives execve, so the key cannot detect an exec; in the normal case the exec tracepoint overwrites the entry, so there is no everyday misattribution. It goes stale when that event is lost (a 256 KiB ring, silently dropped when full) or arrives after the connection is judged, and there is a lost update between the snapshot and the `put` on the miss path. |
| `procfs.rs:135` an in-flight (SCM_RIGHTS) socket has no `/proc` owner | Partly. Real for an fd in flight over a unix socket, where the socket is listed with a live inode and no pid holds it. Refuted for a zombie, whose orphaned socket reports inode 0 and is skipped. The consequence was misstated: attribution does not fail, it returns the uid with `pid: None`, so `exe` rules cannot match and the connection falls to a prompt rather than to a verdict. |
| `procfs.rs:238` exe path taken verbatim, including `" (deleted)"` | Partly. Exact `exe` and `parent_exe` comparisons do fail against the suffix. `exe_glob` mostly still matches, because the matcher leaves `literal_separator` off. The hashing half is refuted: hashing prefers `/proc/<pid>/exe`, which opens the still-live inode of the unlinked binary. |
